# Page Activation Surfaces And Route Subscription Overrides

Alva will treat page activation as three surfaces: declarative `collections:` and `signals:` for normal projection activation, top-level `route_subscriptions:` for per-projection Topic wiring, and raw Phoenix PubSub escape hatches for flows outside the Alva projection model. Declarative activation may derive config from Page Scope, including auth or permission checks, but must not perform control flow; default route subscription inference is retained only when the topic set is deterministic, otherwise page activation fails loudly and requires explicit `route_subscriptions:` for the affected projection. Projection-keyed `route_subscriptions:` entries only override already-active projections and must fail loudly when they reference a projection that is not active. Because active projections are declaration-known, that target validation should fail at compile-time rather than waiting for activation. Declarative activation uses one shared page-level projection namespace across `collections:`, `signals:`, and `route_subscriptions:` targets, so a page may not activate the same Declaration Key as both a Collection and a Signal. Declarative activation uniqueness is consistent across the whole surface: duplicate `collections:`, duplicate `signals:`, duplicate `route_subscriptions:` entries for the same projection, and cross-kind Collection/Signal activation collisions for the same projection key are all declaration conflicts and should fail at compile-time. Overrides are partial rather than all-or-nothing: projections not listed under `route_subscriptions:` continue through deterministic inference and fail loudly if they are not inferable. An explicit empty topic list is authoritative and suppresses inference for that projection, allowing a page to keep the projection active without realtime topic wiring. Callback-based `route_subscriptions:` follow the same rule: returning `[]` is an authoritative dynamic opt-out for the current Page Scope, not a fallback to inference. `nil` is invalid and must fail loudly rather than acting like an implicit opt-out. Callback-based `route_subscriptions:` are also route-lifecycle aware: when Page Scope changes through route lifecycle updates, Alva must re-evaluate those callbacks so realtime Topic scope tracks current Route Params and other page-owned scope. Pages with callback-based `route_subscriptions:` therefore participate in route lifecycle handling even when they have no `reload_on: :route_change` Collections. Explicit `route_subscriptions:` wiring is authoritative and page-owned: Alva validates only the target projection and the topic-shape contract, not whether the supplied Topics can be re-derived from publication templates. Valid Topic lists may still be normalized for transport hygiene, including duplicate removal before subscribe. Pages that need subscriptions outside the projection model should use raw Phoenix PubSub directly. `route_subscriptions:` only owns Topic wiring; it does not replace a Collection's required source or a projection's `on:` PubSub occurrence trigger. For API shape, `route_subscriptions:` uses a top-level list of tuples keyed directly by projection Declaration Key for both Collections and Signals, so projection activation and infra topic wiring stay separate without introducing a second per-kind nesting layer. When multiple active projections resolve to the same concrete Topic, the socket subscribes only once at the transport layer; projection semantics remain independent, so one incoming occurrence may still update multiple Collections and/or fire multiple Signals. Declarative route lifecycle handling first captures the latest Route Params and current Page Scope for active projection wiring, then diffs projection-owned Topic scope by unsubscribing stale Topics and subscribing new Topics before route-change Collection refresh behavior runs. If callback-derived Topic recompute fails during that route lifecycle step, Alva must fail loudly rather than preserving the previous projection-owned Topic set. Declarative activation is therefore allowlisted: only keyword-form `use Alva.LiveView` declarations with `collections:`, `signals:`, and `route_subscriptions:` are valid public page-activation syntax. Legacy tuple forms are not part of the supported surface and should fail at compile-time. The allowlist also applies inside projection activation options: Collection activation uses keyed entries only, with opts reserved for route-owned concerns such as `source_input:` and `reload_on:`. Signal activation uses atom Declaration Keys such as `signals: [:order_fulfilled]`; the client-facing signal name stays in the resource declaration as `name: "order.fulfilled"` and is not repeated in page activation. Signal activation has no opts until a concrete route-owned capability justifies them. Topic wiring for both stays top-level under `route_subscriptions:`. Any other declarative activation key or shape, including legacy `subscriptions:` and declarative `streams:`, is invalid and should raise immediately. Collection activation opts such as nested `params:` / `subscriptions:` remain invalid. Pages that still need non-projection realtime wiring must use raw Phoenix PubSub until they are modeled as Collections or Signals. Activation validation therefore happens in two strict layers: public-surface allowlist validation first, then deterministic inference validation only for still-valid declarative projections. Allowlist failures are compile-time errors because the invalid shape is knowable from the page declaration itself. Deterministic inference failures are activation-time errors because projection/resource wiring and publication matching are resolved there. Deterministic inference means the final Topic set is static, finite, and derivable from projection/resource declarations alone; if Topic wiring depends on runtime Page Scope, callback execution, or ambiguous publication expansion, inference is invalid and explicit `route_subscriptions:` is required. A projection trigger that matches more than one publication is treated as ambiguous even if those publications would expand to a static union of Topics. A single publication may still expand to multiple Topics and remain deterministic as long as that expansion is static and fully derivable from the declaration itself. Publication topic callbacks are never eligible for deterministic inference, even if they would happen to return static Topics for one page instance.
